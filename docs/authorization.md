# Authorization and sign-in

The broker classifies an action as allowed, held or denied. A denied action has no approval path. A held action creates a pending request and returns its ID; the agent retries after the user resolves it in Gaddi.

## Signed decisions

The approval app stores an encrypted, Mac-bound Secure Enclave key blob and its public key in Gaddi's local state directory. Signing requires macOS owner authentication. Touch ID and the Mac password are supported through the system authentication policy. An unavailable Secure Enclave has no software fallback.

Each signature binds the decision to the approval ID, action kind, tab, digest of the displayed detail and timestamp. The app rereads the pending action after authentication. The broker accepts proofs only within sixty seconds and records consumed signatures and operations before acting. Reusing a proof, changing the action or changing a bound target fails. A broker restart returns an unconsumed grant to pending, requiring another approval.

## What a click approval covers

**TX-BIND**. An approved click or key press covers the transaction the user saw, not only the name of its button. "Pay" sends the amount and recipient of its form; "Send" sends the recipients and body of its composer. For the control an action is about, the extension reads the transaction it belongs to (its form, else its dialog, else the nearest container around it that holds a control, such as a mail composer that is no form) and gives the broker a SHA-256 digest of the values of that container's visible controls and of its visible text. Secrets are left out (passwords, hidden and file inputs, card numbers and one-time codes), and so is text that changes by itself: live regions, status lines ("Draft saved"), timers, logs, alerts, progress bars and `output`. Only the digest leaves the page. When the action is held, or is the retry that spends an approval, the broker binds an HMAC of that digest under a key that exists only in this broker run, so the approval state on disk cannot be brute-forced back into an amount, and an approval restored after a restart never matches again (a restart already needs a fresh decision). If the amount, the recipient, the message or the visible total changed after the user approved, the retry is refused (`approval-mismatch`: "the details around that control (amount, recipient, message) changed since it was approved, so nothing was done"), and the extension checks the same digest once more right before it presses, so a change in that last moment gets no input either; the unchanged form still passes. An allowed click is not bound, so a page that changes by itself never stops ordinary work. The limit: text that ticks inside the transaction without any of those markings (an unmarked countdown inside the very form) changes the digest, and the user is asked again; it fails closed, never open. Implemented in `extension/content.ts` (`transactionDigest`, `TX_CHURN`, `checkDescription`), `extension/bg.ts` (the point click's last check) and `daemon/daemon.ts` (`TX_KEY`, `boundDescription`, the click and press branches), with the named refusal in `daemon/approvals.ts` (`consume`). Checked by `tests/gates/approval-binding.test.sh` (broker with a fake page, gated and policy-off: a changed digest refuses a click and an Enter with nothing pressed, the approved one passes once; neither the page's digest nor a value reaches disk or the list, an allowed click is not bound; a restored approval fails after a restart; broker-copy mutations must fail `ASSERT_TX_BOUND`, `ASSERT_TX_RESTART` and `ASSERT_TX_PRIVATE`) and by `tests/bridge/binding.ts` in `tests/bridge/extension.test.sh` (real Chrome: Pay refused after the amount, a point click after the recipient and Enter after the message changed, the approved form pressed; amount, recipient, message, total and a composer's recipient and body each change the digest; a page clock, "Draft saved", a live region, a hidden token and a password do not; mutations that remove the last check or the churn exclusion must fail `ASSERT_TX_FINAL_CHECK` and `ASSERT_TX_CHURN`).

**FRAME-BIND**. A click by point is bound to the document it landed in: Chrome's frame id (0 for the tab itself), that document's own origin, and Chrome's document id, which comes from Chrome's injection result and not from the page. A click by selector inside an embedded document is bound to that document's origin. If, before the approved retry, another site's frame sits at the point (with a button of the same name), or the frame was reloaded, the retry is refused (`approval-mismatch`: "the action now falls in a different document (another site, or the page reloaded) than the one approved"), and the extension compares the same identity right before it presses ("That point now falls in a different document than the one checked"). Implemented in `extension/bg.ts` (`onPage` for `pointTarget`, the describe and the last check of a point click), `extension/content.ts` (`pointTarget`, `checkDescription`) and `daemon/daemon.ts` (the click branch). Checked by `tests/gates/approval-binding.test.sh` (another site's frame and a new document in the same frame refused, the approved one clicked once; the broker-copy mutation must fail `ASSERT_FRAME_BOUND`) and by `tests/bridge/binding.ts` (real Chrome: a payment frame replaced by another origin's copy, then that copy reloaded, at the same point; the mutation that removes the last check must fail `ASSERT_FRAME_FINAL_CHECK`).

## Who asked and why

Every card, banner and phone message names who asked before what: the agent harness, its chat's title, the project, the agent's one-line purpose, the exact action and target, and what approving allows ("This one action, once, within 10 minutes at most." or, for a session grant, every listed action for its length, in that chat only). An agent sets `why` on any call that can be held (open, goto, read a URL, click, type, press, select, upload, eval, signin, extensions); a session grant's label is its why. Its harness names the chat and project: `GADDI_CHAT` and `GADDI_PROJECT` when the adapter starts, or the unadvertised `_context: { chat, project }` argument on each call (Pi's `gaddi-context` extension fills it from the T3 thread). Without either, the project is the git repository the chat runs in. See [chat-title integrations](../integrations/README.md) for Claude Code and Codex hooks and installation snippets.

APPROVAL-CONTEXT: these words are display only. They are cleaned to one plain line (no control or direction characters, no address queries, at most 80, 60 and 160 characters) and frozen when the request is first held; a repeat of the same action keeps its card and first words. They are not in the action hash, the remote digest or any signed message, so they can explain a request but never change what an approval allows. Everything except the harness comes from the agent or its harness, and the cards present it as their words, not as a checked fact.

The approval panel can show a page capture around a click or Enter target. This is context for your decision, not proof that the page is honest. A page can change between inspection and Chrome input. Page-version checks narrow that gap but are not atomic with trusted input.

The status menu updates in place while open. An approval review closes after its queue clears; authentication, visible errors and disconnections keep it open. A manually opened settings panel stays available when an approval arrives and resolves. Closing that panel and receiving a new request starts a fresh review.

## Remembered permissions

Sign-in grants and upload permissions cover one exact origin, including scheme and port. Eligible sends cover that origin plus a specific send kind: Enter and a Send button have separate scopes. Remembering or revoking requires a signed app decision. Payments, deletion, security pages, uploads and denied actions never offer remembered send permission. The default policy remembers nothing.

An eligible upload card offers **Always allow uploads on this site** alongside **Allow once**. Touch ID saves that choice across chats and broker restarts; the panel lists the sites with **Revoke**. Agents cannot add a permission, but they can ask for one.

**GRANT-ORIGIN**. Everything the user grants for a site covers one exact origin (scheme, host and port), plus a path prefix for a session grant rule, and the card that asks says so: a session grant, Always allow (sign-in, uploads, an eligible send), a standing request and the Test zone button show a **Covers** line with the exact scope (`https://app.example.com`, `https://app.example.com/settings`), and the Test zone button names the host exactly (`www.example.com` is never shortened to `example.com`). When a sibling subdomain or the parent domain (same registrable domain on the public suffix list) is plausibly what the agent works on, the card adds one plain line: "Covers only app.example.com; www.example.com is not included." The broker takes those siblings from the tab and acting document of a held action and from the last twelve sites the asking chat acted on (origins only, in memory, gone when the chat ends). The lines are display only, like APPROVAL-CONTEXT: they are frozen on the request, are not in the action hash or any signed message, and name hosts, never a query, a form value or a secret. A later request on a sibling never widens an existing grant, zone or remembered site: it is held and raises its own card (GRANT-FOLD folds it into the chat's waiting card, still as its own rule). Implemented in `daemon/grant-origin.ts` (`coverView`, `originHint`), `daemon/daemon.ts` (`noteSite`, `actionCover`, `requestGrant`, `requestStanding`, the `scope` of a hold), `daemon/approvals.ts` (`scope` on the record) and `app/Sources` (`Approval.covers`, `originHint`, `ApprovalWords.site`, the card's Covers line). Checked by `ASSERT_GRANT_ORIGIN_HINT` and `ASSERT_GRANT_NO_WIDENING` in `tests/gates/session-grant.test.sh` (the card's exact scope and sibling line, no query in it; a grant and a zone on a.example.com hold the same action on b.example.com, example.com, www.example.com and x.a.example.com, and the sibling's grant request raises its own card) with the `SIBLING`, `ZONE_SIBLING` and `ORIGIN_HINT` mutations in `tests/gates/session-grant-mutations.test.sh`, and by `tests/app/card.test.sh` (the Covers and sibling lines on a grant and on an upload card with a zone, the zone button keeping `www.`, no scope line on a one-time payment) and `tests/app/protocol.test.sh` (the scope is parsed and never changes the signed message).

**STANDING.** An agent asks once for standing permission with `browser_grant` and `standing:true`, rules `upload <origin>` or `signin <origin>`. Each rule becomes an ordinary held card of that kind with no tab, worded as a standing request; nothing is done while it waits. Only **Always allow** saves it (the same signed remember choice as above); **Allow once** on such a card allows nothing, and the card closes as soon as it is answered. A site already allowed answers `already allowed` without a card. `browser_approvals` returns `standing`: the remembered sign-in and upload sites, remembered sends and test zones, so an agent can see what runs without asking. Remembered sign-in covers sign-in, creating a new login on that site (NEW-LOGIN) and filling a password from 1Password there (SECRET-FILL). Remembered uploads stay held on built-in and owner-protected addresses and refused hosts; keys, credential files, browser profiles and other protected files remain refused. Each upload allowed by this permission records its reason in the audit.

## Session grants

An agent can ask once, at the start of a chat, to skip a few holds for a while. It calls `browser_grant` with rules of the form `<upload|post|delete> <https address prefix>` (for example `upload https://github.com/settings`), a length from 5 minutes to 12 hours, and an optional label in its own words. Gaddi shows a card with the rules, the length and the label, marked as the agent's description. Only your answer creates the grant, with Touch ID in the Gaddi app or, if you have turned it on, from your phone for a grant of at most 2 hours and twenty rules (see [approvals from another device](#approvals-from-another-device)); nothing an agent or a page says can.


**GRANT-FOLD**. A chat has at most one waiting grant card. A later request from the same chat folds into it: the new card lists every rule asked for so far and the longest time, the folded requests leave the list, and nothing asked for is dropped. An identical retry changes nothing. A rule the chat already holds for long enough, or that a test zone already gives, needs no card at all, and a request made only of such rules is answered at once without one. A fold that would pass the card limit waits as its own request. Folding creates no grant: the user still signs exactly the text on the card, ending the chat cancels its card, and another chat never joins it. Implemented by `daemon/daemon.ts:requestGrant`; checked by `ASSERT_GRANT_FOLD` in `tests/fixtures/broker-checks.ts` and its `FOLD` mutation in `tests/gates/session-grant-mutations.test.sh`. Revisit if the user wants to approve parts of a chat's request separately.

- **What can be waived.** Only an upload hold, a hold on `post`, `publish`, `share` (and their Italian forms) and a hold on `delete`, `remove` and their forms. Payments, purchases, sending email or messages, sign-in, account and security changes, every protected address, guarded keys, navigation holds, extension operations and any verb you add yourself stay held every time. A request that names any of those is refused outright, and Gmail cannot be named at all. A refused or denied action stays refused or denied.
- **Where it applies.** A rule covers its exact site (scheme, host and port) and the path prefix on a path boundary: `/settings` covers `/settings/profile`, never `/settingsX`. A button whose name also contains a verb that is not granted ("Post and pay") stays held, and so does a link that leads outside the granted prefix or to a protected address. An upload still goes through the secret-file refusal first.
- **Whose it is.** A grant belongs to the one chat that asked, identified by the connection its Gaddi adapter keeps open (one adapter process is one chat; an app that runs several conversations through a single adapter shares the grant between them). Another adapter, or a command-line call, gets nothing. It ends when the time is up, when that connection closes, when you end it, or when the broker restarts: grants live in memory only and are never read back from disk.
- **Seeing and ending it.** The panel lists every active grant (who, until when, what, the agent's words) and shows an empty list when there is none. **End now** needs no Touch ID, because it only removes authority. The menu bar shows how many grants are running. `browser_approvals` lists them for the agent too.
- **Audit.** `grant.request`, `grant.start` and `grant.end` (expired, session-ended or revoked) are logged, and every action a grant allowed carries `grant: <id>`.

What this does not give you: a grant trusts the whole chat inside its rules, including anything a web page talks that chat into doing there. An upload grant lets the chat attach any file from your home folder that is not on the secret-file list to that page. Keep the rules narrow and the time short. The chat identity is a random ID held by the adapter process, not an authenticated operating-system identity: the broker never lists or logs it, but a process under your account that learned it could use the grant.

The user can also edit the local policy. That file and the broker run under the same macOS account as the agents: signed UI decisions do not make them tamper-proof against a process with full access to that account. Policy changes can relax defaults, including the upload hold. See [policy configuration](../install/README.md#policy).

## Test zones

**TEST-ZONE**. A test zone is a whole site (exact origin: scheme, host and port) that the user marks as his own test ground. On it, for every agent and chat and for command-line calls, with no expiry until he removes it, these run without asking: sign-in with the login he stored in 1Password for that site, uploads, posts, deletes, and account or security changes (password, two-step, recovery, closing the account, unsubscribing, and opening the site's own security and account-closure pages). Still held every time: payments, purchases, orders, transfers and their pages (a page can claim to be a test, so Gaddi never treats a payment as fake), and sending messages, because Gaddi cannot show that a recipient is a test account (a send he remembered for that site keeps working through its own rule). A mixed name such as "Post and pay", a link leaving the zone or reaching a payment page, and secret files stay held or refused. Refused hosts, his own protected addresses and identity providers (Google, Apple, iCloud, Microsoft, 1Password, Okta, Auth0, GitHub) can never be zones, because a zone there would act on his real identity. Typing literal text into password fields stays refused everywhere (a 1Password fill follows the sign-in rule, SECRET-FILL). Enter on a form keeps grant parity (posts and deletes only), because the broker cannot see where a form submits; account and security changes need a click. His own refused hosts and protected addresses win over a zone, sign-in included.

- **Setting one.** In the Gaddi review window, a waiting upload, post, delete or grant card offers **Test zone: always allow on <site>**: one Touch ID makes its sites zones and answers that request. The **Test zones** section lists them, adds one by address (Touch ID) and removes one with **Remove** (no Touch ID, because it only takes authority away). A waiting grant request that asks only for what the zones now give is closed.
- **Where it lives.** The user's policy overlay (`zones.sites`), written only after a verified signature over `zones.add|<site>|<ts>`. It survives restarts, unlike a session grant.
- **The limit.** A zone covers a site, not an account: if the site is signed in to a real account in his Chrome, the zone covers that account too. Use zones for sites, ports or staging hosts that only ever hold test data.
- **Audit.** Every action a zone allowed carries `zone: <site>`. A zone the user also made a sandbox allows payments and sends too (see [Sandboxes](#sandboxes)).

Implemented by `daemon/grants.ts:checkZone`, `daemon/policy.ts:setZone`, `daemon/proof.ts:zoneAddMessage` and the `zones.*` methods in `daemon/daemon.ts`; checked by `ASSERT_ZONE` and its `ZONE`, `ZONE_REASON`, `ZONE_MIXED` and `ZONE_PAYMENT` mutations, and by `tests/policy/zones.test.sh` (sites that can be zones, sign-in). Revisit if he needs a zone narrower than a site (one account or one path).

## Sandboxes

**SANDBOX**. A sandbox is a test zone the user also marked as a place where nothing real can be spent or sent. On it, for every agent and chat and for command-line calls, until the user turns it off, everything a test zone allows runs without asking, and so do payments, purchases, orders, transfers and their pages, and sends (messages and email). No hold remains on that site except these: a denied action stays denied, a guarded secret file stays refused, extension operations stay held, a click inside an embedded document Gaddi cannot inspect stays held, a guarded key and an address the user protected still win, and a link or an embedded document that leaves the sandbox is judged by its own address (FRAME-SCOPE: the tab, the acting document and a link's destination must all be covered). Sites that can never be test zones (identity providers such as Google, Apple, iCloud, Microsoft, 1Password, Okta, Auth0 and GitHub, Gmail and the other refused hosts) can never be sandboxes either.

- **Payment provider test mode.** While at least one sandbox exists, a Stripe-hosted test Checkout session, an address of exactly the form `https://checkout.stripe.com/c/pay/cs_test_<id>`, counts as a sandbox too, so a sandbox app can hand its agent to its Stripe test checkout and pay with a test card. Stripe issues the `cs_test_` session id and its test mode cannot move real money. A live session (`cs_live_`), any other Stripe address and every other payment provider stay held.
- **Setting one.** In the Test zones section of the Gaddi review window, each zone offers **Make sandbox**: one Touch ID signs `sandbox.add|<site>|<ts>`, a message of its own, so a `zones.add` signature can never turn a sandbox on. A site must already be a test zone. **End sandbox** turns it back into a plain zone, and **Remove** removes the zone and its sandbox; neither asks for Touch ID, because they only take authority away.
- **Where it lives.** The user's policy overlay (`zones.sandbox`, every entry also in `zones.sites`). A hand-edited sandbox that is not a zone, or that names a site that can never be a zone, stops the broker from starting.
- **Seeing it.** Every page of a sandbox site shows a red band across the top of the window, drawn by the extension in a closed shadow root that takes no clicks and comes back when the page removes or hides it. The band is for the user's eyes; the broker never reads it. `look` on a sandbox page carries `sandbox: <site>`, said by the broker from its policy, so a page that hides its band cannot hide the sandbox from agents.
- **Audit.** Every action a sandbox allowed carries `sandbox: true` and `zone: <site>` (`https://checkout.stripe.com` for a Stripe test session).

What this does not give you: a sandbox covers whatever the site does with your browser's session there. If that site holds a real payment method, a real customer list or a live payment key, the agent can use them without asking. Make a site a sandbox only when everything it can charge or send goes to test accounts.

Implemented by `daemon/grants.ts:checkSandbox` and `sandboxCovers`, `daemon/policy.ts:setSandbox`, `daemon/proof.ts:sandboxAddMessage`, the `sandbox.*` methods in `daemon/daemon.ts`, `extension/sandbox.ts` (the band) and the Test zones section in `app/Sources/ApprovalCard.swift`; checked by `ASSERT_SANDBOX` in `tests/fixtures/broker-checks.ts` and its `SANDBOX`, `SANDBOX_LEAVING`, `SANDBOX_FRAME`, `SANDBOX_LIVE`, `SANDBOX_MESSAGE`, `SANDBOX_AUDIT` and `SANDBOX_REMOVE` mutations in `tests/gates/session-grant-mutations.test.sh`, by `ASSERT_SANDBOX_SITE` in `tests/policy/zones.test.sh`, by `tests/bridge/sandbox-band.ts` in `tests/bridge/extension.test.sh` with its `GADDI_BRIDGE_BREAK_SANDBOX_BAND` falsification, and by the Test zones checks in `tests/app/protocol.test.sh`. Revisit if another payment provider's test mode is needed, or a sandbox narrower than a site.

## Standing allowances

**GITHUB-OWN**. On the user's own GitHub accounts, `https://github.com/ABCastor/` and `https://github.com/Anneo22/`, agents do repository, issue and pull-request work without asking: the post, publish and share holds and the delete and remove holds on issues, pull requests, comments, branches and files, for every agent and chat and for command-line calls. Still held every time: any address with a `settings`, `billing`, `sponsors`, `sponsorships`, `security`, `payment` or `payments` segment (repository, organisation and account settings, which include deleting or transferring a repository), `github.com/settings`, every protected address, anything outside those two prefixes (other accounts, `github.com/orgs/…`, gists), uploads, payments, sends and sign-in. The scan is the session grant's own: a mixed name ("Delete and pay") stays held, and so does a link leaving the prefix or reaching a settings page. A segment is read decoded and in any case, so `%73ettings` and `SETTINGS` are still settings, and an account name matches in any case, as GitHub's does. GitHub stays impossible as a test zone or sandbox.

- **Where it lives.** The shipped defaults (`allowances.github_own` in `policy/policy.default.json`), one list of account prefixes of exactly the form `https://github.com/<account>/`. The user's overlay can replace the list or empty it (`[]` turns it off); it cannot name anything but a whole GitHub account.
- **Audit.** Every action it allowed carries `allowance: github-own`.

What this does not give you: an account prefix covers every repository under it, including one a page talks the agent into editing there. Repository deletion and transfer stay held because they live under settings.

Implemented by `daemon/grants.ts:checkGitHubOwn` and `githubOwnCovers`, `daemon/policy.ts:githubOwnPrefix` and the grant check in `daemon/daemon.ts`; checked by `ASSERT_GITHUB_OWN` in `tests/fixtures/broker-checks.ts` and its `GITHUB_SETTINGS`, `GITHUB_OTHER`, `GITHUB_ENCODED` and `GITHUB_AUDIT` mutations in `tests/gates/session-grant-mutations.test.sh`, and by `ASSERT_GITHUB_OWN_PREFIX` in `tests/policy/zones.test.sh`. Revisit to add a GitHub account, or to allow uploads (attaching files to issues) there.

## Clicks by point, and inside embedded pages

**POINT-CLICK**. An agent may name a point in the tab's own viewport, the place a screenshot shows, and Gaddi presses it with the same trusted input a person's mouse sends: the point goes to Chrome untouched. The point is not a way around the gates. Before pressing, Gaddi reads what is really under that point, following it into embedded documents, and that element's name, link destination, page address and frame address cross the same click, navigation, remembered-send, grant and zone checks a selector click crosses. A covered button is clicked on the visible part of its face; a marker that takes no pointer events is not treated as an obstacle; the checkbox inside a verification widget is judged as that checkbox, never as the frame around it. A point over a document Gaddi cannot inspect (another extension's page, a sandboxed document, a frame still loading) has no name to check, so it is held as "click inside an embedded document Gaddi cannot inspect" and only an approval from the user runs it. The audit records the point, and the embedded page when there is one. `at` and `frameId` are alternatives: a point is always in the tab's viewport, so it never has two coordinate systems to disagree about.

**FRAME-SCOPE.** A click or a key that happens inside an embedded document is judged on that document's own address as well as on the tab's: a refused host (Gmail) still refuses inside an embed, a protected address still holds, a remembered send is remembered for the site that acts, and a session grant or a test zone named for the page around a third-party embed does not cover what that third party does. Both addresses must allow, so acting through one cannot escape the rules of the other.

**FRAME-KEYS.** Keyboard input reaches the document that holds the focus. Keys aimed inside an embedded document are allowed once that document is the inspected target (its own field, its own checks) and refused when only the page around it was checked, or while the focus is somewhere else. A key press whose focus Gaddi cannot place inside the inspected document is never sent.

**CHOICE-PROSE**. A click that toggles a choice (checkbox, radio, option, switch, or the label of one) performs nothing by itself: its words describe what is being chosen, not what the page will do. Such a click is gated on an action verb only when the name reads as an order: the verb leads a label of at most six words (not a sentence) and is either the whole name or followed by its object, an amount (a digit or a currency sign) or a determiner or pronoun (my, the, this, all, it, now, and their Italian forms). "Delete", "Send now", "Delete all my files", "Pay £10" and "Elimina il conto" still ask; "the windshield centre post reduces blind spots" does not, and neither does a verb that starts the name of the thing chosen: "Pay Monthly Mobile" (a service type on case.ombudsman-services.org, held as a payment on 12 Nov 2026), "Post Office collection", "Paga con carta". A button, link or other control is never read this way: "Pay now" and "Pay £10" buttons are held wherever the verb appears. The submit that follows a choice is gated on its own name and on the choices it sends (COMMIT-CHOICES).

**SELECT-CHOICE**. A native select can act the moment it changes, so `browser_select` is judged as the click on that choice would be. Before the value is set, Gaddi reads the option it picks (the first with that value, as the page's own select does: what the list shows, its text, its own label and its group's label) and the select's accessible name, and judges each by CHOICE-PROSE on the document that holds the select and on the tab around it. "Delete all", "Elimina il conto", "Pay £10", a list named "Delete", or a group labelled "Delete" ask; "Pay Monthly Mobile", "Post Office collection", countries and dates are chosen. The card reads "select “Delete all (Account action)”"; the approval covers that option of that list, so the same value picking another option is a different action, and the page must still show the judged option and name when the value goes in, or nothing is set. Session grants, test zones, sandboxes and the GitHub allowance treat a select hold as they treat the click on that choice; the phone does not answer it (remote approval covers clicks, keys and uploads), so it waits for Touch ID.

**COMMIT-CHOICES**. A button carries out the choices that are on where it acts: its form (with every control that names that form), else the dialog it sits in, else its page minus the choices of other forms. Checked boxes and radios, selected options, and ARIA choices marked checked or selected count, whoever turned them on (the page, a key, a click, an earlier visit). A click on a button, Enter that submits or presses one, and Space on one are held when one of those choices is an instruction: a hold verb other than the naming verbs below leads its name, in at most six words, whatever follows the verb. "Delete files older than a month", then "Save", asks (card: "click “Save, with “Delete files older than a month” chosen”"); so do "Remove old backups", "Elimina i file vecchi", "Close account and keep data" and "Unsubscribe from all lists" sent by "Save", "Apply" or Enter. The choices are bound to the press like the button's own name: a page that turns on another one between the check and the press gets nothing done. A delete grant covers such a commit only where it would cover the choice's own verb.

The naming verbs are the money, send and post verbs (pay, buy, order, checkout, transfer, top up, send, post, publish, share and their Italian forms). A chosen name led by one of them is not judged again at the commit, because a lexical gate cannot tell "Pay statement balance" from "Pay Monthly Mobile", the contract the user chose to let agents pick (12 Nov 2026); holding the "Continue" after it would be the same false hold one click later. They remain held when they read as an order at the click, by key or in a select ("Pay £10", "Send me a copy", "Share all my photos"), and their own buttons, Enter, payment pages and links stay gated; no grant or zone ever waives money or sends.

The limits, stated: a chosen instruction of more than six words reads as a sentence ("Delete all files that are older than thirty days" then "Save" is not held), as CHOICE-PROSE reads it when clicked; a commit made by a page script on its own timer, or by a link styled as a button, is not a button press and is not judged; a choice drawn as a plain element with no checkbox, radio or option role (and no checked or selected state) is invisible to the gate.

**KEY-CHOICE**. A key can pick what a click would have to ask for, so every key is judged on what holds the focus. On a focused select, a letter or an arrow can pick any enabled option, so the key is held when any of them, or the select's name, reads as an order; on a radio, the arrows reach every radio of its group; a checkbox or switch toggles with Space; a list or menu that keeps the focus and points at an item (`aria-activedescendant`) picks that item. Tab, Shift+Tab and Escape only move the focus or close, and are never held for a choice. **DRAG-HOLD**. A drag and a press-and-hold are clicks that keep the button down, sent as the same trusted input as a point click (Chrome's debugger, `Input.dispatchMouseEvent`), never as page events. `browser_click` takes `to:{x,y}` to drag from `at` to that point (both in the tab's viewport, as a screenshot shows them, because a reference would be scrolled into view and move the other point) and `holdMs` (1 to 10,000) to keep the button down that long; a drag moves through that time (300 ms by default) in steps of about one frame, with the button held, and a hold by reference presses the control's centre. From a terminal: `gaddi drag <tab> x,y x,y [--hold-ms N]`, `gaddi hold <tab> <ref|x,y> <ms>`, or `click --at x,y --to x,y`, `click … --hold-ms N`. **PUZZLE**. An agent answers a picture, tile or grid challenge itself, in the user's own session, with no card and no help from him. The widget is already named: `look` lists every document, and one on a verification provider's address is marked `challenge: true`. Gaddi crops a screenshot to that document and says where the crop sits in the tab (`box`), so a pixel in the picture is a point: x = box.x + px × box.width / width, y likewise. The agent reads the picture, presses what it chose with `click --at` (trusted input, audited as a point inside that document, with the picture recorded as `shot`), and presses the widget's own verify button. Nothing here solves, reads or forges a token, and no synthesised event is ever used, because the real widgets ignore them. A letter or picture drawn too small to read is read the way a person reads it: `screenshot --frame <id> --zoom x,y,w,h` magnifies one region of that document, losslessly and up to four times its size, and the answer says where the close-up sits in the tab, so a point in the magnified picture is still a point to press. A widget that rejects an answer starts a new picture: take it again and try again, and say what was tried. The limit is the model reading the picture, not the press. What a challenge asks for is a person's judgement; the judgement is the agent's, the input is the person's own.

**PUZZLE-LIMIT.** The challenge is answered as a person would answer it: the picture is looked at, the tiles are pressed, the same request goes out. Gaddi does not intercept, rewrite or replay the provider's traffic, does not farm or outsource the answer, and does not hide that the session is driven by an agent. If a provider demands a different proof, such as a phone call or a hardware key, that stays with the user, because it is his identity and not his judgement.

Rules of thumb: the widget's frames are the only documents this applies to (a `challenge` frame), and a click whose name is a real action still crosses the hold verbs, so a challenge that asks you to "Post" a response is still a post. Screenshots of a challenge are kept only as the action's audit record, in the profile's own `shots` folder.

## Page scripts

**EVAL-READONLY**. `browser_eval` reads; it cannot act. Chrome's JavaScript engine runs the script in its side-effect-free mode, the mode DevTools uses to preview an expression while you type: any call or store the engine cannot prove harmless is stopped before it happens, and the agent gets `EVAL_READ_ONLY` with nothing done. That covers every way a script could reach past the gates: clicking, submitting or `requestSubmit`, dispatching mouse, keyboard or submit events, setting `location`, `window.open`, history changes, `fetch`, `XMLHttpRequest`, `sendBeacon`, image loads, typing into fields, focus, cookies and storage, changing page state or the DOM, timers, promise callbacks and `async` continuations, getters, proxies, `eval` and `new Function`, and reaching into another frame. The check is the engine's, not a list of words, so renaming, wrapping, encoding or `try`/`catch` changes nothing; it applies to whatever code the script reaches, including the page's own functions. Reading works: text, attributes, `querySelector`/`querySelectorAll`, forms and their values, geometry, computed styles, page variables, same-origin frames, and top-level `const`, `let` and `class` (the script runs inside a block). Some reads the engine cannot prove harmless are refused too: `getElementById` (use `querySelector('#id')`), `matches`, `closest`, `matchMedia`, `Object.assign`, object spread, `Object.fromEntries`, `new URL`, top-level `var` and `function` declarations, and waiting on the page's own promises. To act, an agent uses click, type, press, select and scroll, which the gates judge.

A script that has to change the page is the user's call. With `write: true` (CLI `--write`) the broker holds it: the card says "Run a script", shows the script as it will run (credential values in URLs redacted) and binds the approval to that exact script, tab and caller, once. No session grant, test zone, sandbox, standing allowance, remembered site or phone approval answers it, because the broker cannot read what a script will do. The MCP tool takes no `why` (its schema is at the tools/list budget), so the card's Why line is empty from MCP and filled from the CLI's `--why`; the agent learns about `write` from the `EVAL_READ_ONLY` refusal. A script to approve may be at most 2,000 characters, so the card shows all of it. The deny patterns and the password refusal apply to it as to any evaluation. With the policy off, every evaluation runs with its side effects, as before.

What this does not cover: Gaddi's other tools still act through the gates as described above, and the page's own scripts keep running by themselves. An approved writing script can do anything a page can.

Implemented by `extension/bg.ts` (`throwOnSideEffect`, `EVAL_READ_ONLY`), `daemon/policy.ts` (`checkEval`, `EVAL_WRITE_HOLD`), `daemon/daemon.ts` (the `write` parameter and `EVAL_WRITE_LIMIT`), `daemon/approvals.ts` (the script as the card's detail) and `app/Sources/ApprovalCard.swift` (the Script line). Checked against a real page by `tests/bridge/eval-readonly.test.sh`: 48 ways to act are refused with nothing reaching the page or the fixture's server, eleven reads return their values, an approved script does act (the oracle's control), and switching the engine check off must fail `ASSERT_EVAL_BYPASS_REFUSED`. The broker side by `tests/gates/eval-write.test.sh` (a read is sent without write; a writing script is held, shown exactly, bound to itself and single use; shape, length and deny patterns), falsified with the gates off, and the card by `tests/app/card.test.sh`. ## The review window

The menu bar's "N actions are waiting for you" row opens the review window. A banner click opens it on everything waiting. Opened by the user, it is a regular app window (with a Dock icon while open) that stays above other windows until closed; opened automatically, it still takes no focus. Requests are grouped by the chat that asked (harness and chat title); a group of two or more has **Approve all** and **Deny all**, one Touch ID that signs each request separately and skips any that changed. Banners are one per chat and are replaced as its requests arrive: the title says who asked, the subtitle the action, the body why.

## Approvals from another device

A separate program of yours, for instance a Telegram bot running on your own machine, can answer some of Gaddi's requests so that you can say yes from your phone. It is **off by default**. **Only your Touch ID in the Gaddi app turns it on.** **Anyone who can reach the socket can turn it off**, because turning it off only removes authority. It covers only the explicit upload/post/delete tier, and only requests Gaddi itself marks as answerable. Deletion can be permanent; uploads and publishing can expose data.

### What it can answer

While it is on, a waiting request carries `remote: true`, a `digest` and its enrollment `epoch` if it is one of these, and only then:

- **An upload, a post or a delete** that a session grant on that page could waive. The hold is the same upload, post or delete hold; the page is an address a grant rule can name (https, or http on this Mac) and is not protected (payments, account and security pages, Gmail); every action word in the button's name is one of those three, so "Post and pay" is not; and a link's destination is on the same site and not protected. Gaddi judges this with the very scan session grants use, from the page address as it was when the request was held (a query can make a page protected), and again every time the request is listed or answered.
- **A session-grant request of 2 hours or less and no more than twenty rules.**

Never, whatever the program sends: payments and purchases, sending email or messages, sign-in, account and security changes and every protected address, guarded keys (such as Cmd+Enter in Gmail), navigation, extension operations, script evaluation, and anything Gaddi did not mark. They are outside this remote/session-grant path; separately remembered permissions are described above.

### The contract

1. **Key.** The program generates its own Ed25519 key pair and writes the public key, as an SPKI PEM (`-----BEGIN PUBLIC KEY-----`), to `~/Library/Application Support/Gaddi/remote-approver.pub` (`$GADDI_REMOTE_KEY` overrides the path). That file is only a candidate. It authorizes nothing, a private key or any other kind of key is ignored, and once you have turned the feature on, changing the file does nothing until you turn it on again.
2. **Turn on.** In the Gaddi panel, **Approvals from your phone**, **Turn on…** shows the waiting key's fingerprint (the first 16 hex digits of the SHA-256 of its DER SPKI, in groups of four) so you can compare it with the one the program shows you, then asks for Touch ID. Touch ID signs `remote.enable|<fingerprint>|<ts>` over the full fingerprint. Gaddi stores that key (`remote.json`, owner-only) and uses only it from then on. The saved choice survives a restart; a damaged file means off.
3. **Listen.** Connect to the socket and send `{"id":1,"method":"events.subscribe","params":{"caller":"marcus"}}`. Act on `approval.pending` events whose `approval.remote === true`, or poll `approvals.list` and keep the rows where `remote === true`. Listen for `remote.changed` too: it announces on and off, and after it you should list again, because requests that were already waiting change their flag.
4. **Show and answer.** Show the user `caller`, `kind`, `detail`, and `url`. A request that has a page capture also carries `imagePath` (a JPEG on this Mac) and `box` (the target, in the picture's pixels); showing the picture with the target outlined lets him see what he is approving, as the Mac does. When he decides, send `{"method":"approval.remote","params":{"id":…,"verb":"grant"|"deny","nonce":…,"ts":…,"sig":…}}` where
   - `sig` is the base64 Ed25519 signature (64 bytes) of the UTF-8 text `gaddi-remote-v2|<epoch>|<verb>|<id>|<kind>|<digest>|<nonce>|<ts>`;
   - `epoch` is the exact 32-hex enrollment generation from the displayed immutable card, never refreshed behind that card;
   - `digest` is the `digest` field of the request, the SHA-256 hex of `<kind>|<id>|<detail>`, so a decision cannot be moved to another request or to a request whose text changed;
   - `nonce` is 16 to 128 characters of `A-Za-z0-9_-`, never reused;
   - `ts` is the time in whole milliseconds, within 120 seconds of Gaddi's clock.
5. **Off and status.** `remote.status` reports `{enabled, fingerprint, enabledAt, epoch, candidate}`. `remote.disable` stops new decisions and revokes unused remote-derived approvals and active remote-derived grants; it needs no proof. It cannot undo an action already dispatched.

An answer is refused with `denied` while the feature is off, with `approval-invalid` if the request is not waiting or cannot be answered this way (one answer for every such case), and with `proof-invalid` for a wrong key, a changed field, a stale time, a malformed nonce or a replay. The signature and the nonce are written to the same durable journal as Touch ID proofs *before* Gaddi acts, so a replay fails after a restart too. An approved action is then retried by the agent with `approval=<id>` exactly as after a Touch ID approval, and it still works once and only for the exact action. An approved session-grant request starts the grant as Touch ID would, and the grant is listed and audited as approved from the phone. A denial closes the request.

### Seeing it and ending it

The panel section is always shown. Off, it says in two sentences what it would allow and what stays Touch ID only. On, it shows the key's fingerprint and since when, with **Turn off**, which needs no Touch ID. The menu bar says when it is on. A waiting request it may answer says "Can also be approved from your phone", and the last ten answers it gave are listed with what, where and when. From a terminal, `gaddi remote` shows the status and `gaddi remote off` turns it off; there is no `on`, because turning it on is Touch ID in the app. No agent tool can answer or turn it on or off; `browser_approvals` lists waiting requests as before, so an agent can see which carry the flag. The audit records every answer as `approval.remote` with `approver: remote`, the request, its kind, the verb and the outcome, and every turn-on and turn-off; it never records a signature or a nonce.

V2 signs the enrollment generation as well as the immutable request. Turning on creates a fresh random 128-bit generation. An older saved enrollment derives a stable generation from its fingerprint and enable time; this preserves an existing owner choice, while refusing all old v1 signatures. Ordinary restart keeps the generation. Disable/re-enable changes it even for the same key, so old phone cards cannot regain authority. Gaddi and its Marcus client must upgrade together; an old client fails closed.

### The limit

The key of the phone approver is a file that any process running as your macOS user can read, so this path is weaker than Touch ID: a program on this Mac that can read that key can approve exactly what is described above, and nothing beyond it. That is why the scope is small, why it is off until you turn it on, and why it is one signed answer per request. It does not weaken what stays Touch ID only. As with everything else here, a process that can write Gaddi's own files can do more: it could write `remote.json` and restart the broker, as it could replace the Touch ID verification key `approver.pub`; the signed turn-on protects against everything that cannot write there. The facts Gaddi keeps about a waiting request live in memory only, so a request that was waiting when Gaddi restarted can only be answered with Touch ID until its agent asks again; Gaddi then announces it again with `approval.pending`. To change the key, turn the feature off, let the program write its new key, and turn it on again.

## Optional longer waits and larger cards

These options ship inactive. Omitting them preserves the configured request expiry and the maximum of twenty rules. These rules describe the optional approval settings; they do not claim repository-wide coverage.

**AUTH-WAIT.** An eligible pending request may wait longer for an answer, while usable signed authority stays within `ttl_minutes` and remains single use. Only session grants and the same upload/post/delete tier eligible for remote approval use the longer wait. Payments, purchases, sign-in, sends, security changes, protected pages and unknown classes keep their existing expiry. A pending grant still needs its live chat; ending that chat cancels it. Restart never restores granted authority. A monotonic deadline prevents backward wall-clock changes from extending usable authority. Verification crossing the pending deadline fails after spending the proof. Invalid restored timestamps are rejected. New admission stops at one hundred live approval records and their bounded captures. Valid older state with more than one hundred records is retained; it must fall below the limit before a new request is admitted. Capacity refusal never evicts an existing request.

**AUTH-PHONE.** Phone decisions bind immutable request data and enrollment generation, remain signed and one-use, and are revoked on disable. All affected in-memory authority is removed even if saving, expiry bookkeeping or reporting fails; an error still reports the failure. Enrollment still requires Touch ID. The local-key trust limit above remains explicit; no per-button biometric or phone-only-key claim is made. Implemented in `daemon/remote.ts`, `daemon/daemon.ts`, `daemon/grants.ts` and the paired Marcus client; tested by the remote gate, generation/revocation checks, `tests/policy/remote-revocation.ts` fault recovery and mutation suite.

**AUTH-LARGE-GRANT.** The user can raise the Mac card limit from twenty to at most one hundred rules. Every rule is validated, displayed and signed in full. Allowed verbs, protected addresses, chat isolation, revocation and maximum duration stay the same. Phone-approved grants stay limited to twenty rules and two hours. These bounds keep longer waits and larger grants explicit and opt-in.

The optional policy overlay fields are:

```json
{
  "approvals": {
    "ttl_minutes": 10,
    "wait_minutes": 720,
    "grant_rules_max": 100
  }
}
```

`wait_minutes` accepts whole minutes from 1 through 720; omission uses `ttl_minutes`. `grant_rules_max` accepts whole counts from 1 through 100; omission uses twenty. Overlay validation rejects malformed values before the broker listens. Quit Gaddi and stop the broker before an owner-approved overlay edit, then restart through the installation's existing service procedure. Never edit running application state externally. Keep other overlay fields when editing. Removing the two optional fields restores the original settings.

A waiting request and a permission have different lifetimes. Answering near a request's expiry does not extend it past that deadline; otherwise the signed action has at most `ttl_minutes` left. A session grant's duration starts when approved and ends independently of the request's waiting time.

These options do not make an individual approval portable across tabs. Site, verb and a control's name cannot establish which record, account or content a page will affect. Individual approvals retain their exact tab/action binding. A deliberately scoped session grant is the existing way to authorize eligible actions across replacement tabs: the user approves the named site, path, verbs, chat and duration, rather than one particular target. It does not claim to approve one exact object.

Implemented in `daemon/approvals.ts`, `daemon/daemon.ts`, `daemon/grants.ts`, `daemon/policy.ts` and `daemon/remote.ts`. Exercised by `tests/policy/approval-wait.ts`, `tests/gates/approval-wait.test.sh` and the existing grant/remote gate and mutation tests. The new gate runs a real isolated broker and fixture Chrome transport; it is not a real Telegram or biometric demonstration.

## 1Password sign-in

Install the 1Password CLI. Since 6 Nov 2026 Gaddi reads 1Password only as the agents' service account: each `op` call reads the token from `~/.config/op/agent-rw-token`, runs with a home of its own (`~/.config/op/isolated-home`) and with every inherited `OP_*` variable removed, so it never reaches the 1Password desktop app and there is no desktop fallback (a desktop prompt blocked every sign-in whenever nobody was at the Mac). Only Logins in vaults that account can read (Automation or Shared) are usable; Personal is not. It searches Login items for the tab's host or registrable domain, requires HTTPS except for local testing, and never accepts an unrelated selected item. Multiple matches return `choose`; specify an item title or ID to select one.

```sh
gaddi signin <tab-id>
gaddi signin <tab-id> --item '<login-title>'
gaddi signin <tab-id> --approval <approved-id>
```

**OP-DIAGNOSTICS.** A 1Password failure still answers `needs_you` with the same `PASSWORD_UNAVAILABLE` reason, and adds `category` (`<step>:<kind>`) and `elapsed_ms` to the reply and to the sign-in's audit row. Step `1password` is the item list, `credentials` the read of the chosen item. Kinds: `binary-missing`, `token-missing`, `token-unreadable`, `token-empty`, `home-unavailable`, `list-`/`get-` + `exit`, `timeout`, `oversize`, `spawn` or `malformed`, `schema-missing-` or `schema-duplicate-` + `username` or `password`, and `budget` (the sign-in's 15 s ran out). Neither carries `op` output, item contents, a credential or the token. The username and password are chosen by their 1Password purpose (USERNAME, PASSWORD), not their label, so a renamed username field or a second field labelled "password" still works; a field without a purpose is matched by exact label. Gaddi first asks `op` for the two labelled fields and reads the whole item only when that cannot give one pair. A password-only page (a "confirm your password" step) needs no username. Implemented in `daemon/signin.ts`; exercised with a fake `op` by `tests/signin/op-failure.test.sh`.

Gaddi fills supported one-step and two-step forms and an available TOTP. Captchas, passkeys, an unreachable 1Password and unsupported verification return `needs_you`, and the ones that need the user's own hand raise OWNER-NEEDED. An agent can continue a visual challenge with the ordinary screenshot/click tools under PUZZLE and PUZZLE-LIMIT; the sign-in helper itself does not solve it or grant a privileged bypass. A `signed_in` outcome requires the password field to disappear and the URL or page to change; it is a page-state heuristic, not server-side proof of authentication.

### When the user must act

**HANDOFF-SHOW.** Agents work in Gaddi's own Chrome window, which you may keep minimized. An explicit handoff, `browser_show` or `browser_open` with `foreground:true`, makes the tab visible: it becomes the active tab of its window and, if that window is minimized, the window is restored (`state: normal`, with no size or position given, so it comes back where you left it). On macOS a restored window comes to the front. Only the window holding that tab is touched: no other window is restored or focused. Whether `show` also asks for focus stays the show policy's (`browser.show: front`; the default, `attention`, bounces the Dock icon). Background calls (open without `foreground`, look, click, type, and the rest) never restore, focus or ask for attention, so the window stays as you left it. Observed limit (23 Nov 2026): headful Chrome on macOS creates Gaddi's window normal, not minimized, although Gaddi asks for minimized; it stays unfocused. Implemented in `extension/bg.ts` (`handOff`, the show and open branches). Checked by `tests/bridge/handoff.test.sh` (real Chrome for Testing, disposable profile: show and foreground open from minimized restore the window with your bounds and the right tab active; background open, look, click and type leave it minimized and unfocused; an unrelated minimized window stays minimized, unfocused and in place; mutations must fail `ASSERT_HANDOFF_SHOW`, `ASSERT_HANDOFF_OPEN`, `ASSERT_HANDOFF_QUIET`, `ASSERT_HANDOFF_OTHER_WINDOW` and `ASSERT_HANDOFF_BOUNDS`).

**OWNER-NEEDED.** When a sign-in answers `needs_you` because only you can act (a security key, passkey or phone prompt after the password, a verification step, a one-time code Gaddi does not have, a page with no form it can fill, or a locked or unreachable 1Password), the broker also tells you directly: the event `owner.needed` carries the tab, the site's origin, the step and a reason from a fixed table, and the Gaddi app shows "Gaddi needs you on <origin>: <reason>". It never carries a URL path or query, a username, an item title, page text or any secret. An approval card that already asks, a no-login or choose answer, a failed or changed form and all ordinary work emit nothing. One notice per tab and step while it lives, so an agent polling `signin` cannot repeat it. Clicking the notification shows that tab through the `browser_show` path (`owner.show`, only for a live notice). The notice is information, never a decision: clicking it is not consent, answers no approval and does not end it, and dismissing it does nothing at all (cancel means: the notice goes unanswered until it ends). After you act, the agent's next `signin` or `look` judges the real page. The notice is withdrawn (`owner.withdrawn`, with why) when the same tab reports `signed_in`, its tab closes (through Gaddi, or in Chrome, seen by the broker's 30-second sweep), the agent's session ends, Chrome reattaches (tab numbers may be reused), or after ten minutes unanswered. The broker wakes the app for a notice; the app reads live notices from `owner.notices` and shows each once. Implemented in `daemon/owner-needed.ts`, the sign-in `finish` path and tab bookkeeping in `daemon/daemon.ts`, and `OwnerNotice` in `app/Sources/Protocol.swift` and `AppController.swift`. Checked by `tests/signin/owner-needed.test.sh` (real broker, fake `op` and bridge, canary strings for every secret and the page's path and query; broker-copy mutations must fail `ASSERT_OWNER_NEEDED_EMITTED`, `ASSERT_OWNER_RATE_LIMIT`, `ASSERT_OWNER_WITHDRAW_SIGNED_IN`, `_CLOSED`, `_GONE`, `_SESSION`, `_REATTACH`, `ASSERT_OWNER_EXPIRES`, `ASSERT_OWNER_NO_LEAK`, `ASSERT_OWNER_QUIET` and `ASSERT_OWNER_SHOW_ENDED`) and `tests/app/protocol.test.sh` (shown once, withdrawn with the broker, a notice with a path, query or multi-line reason dropped; mutations of those checks must let one through).

**SECRET-FILL.** `browser_type` with `secret:<1Password item title or ID>` (CLI `gaddi type <tab> <field> --secret <item>`) fills one password field with that Login's password. The item must match the tab's site the same way a sign-in does (host or registrable domain, HTTPS or local), the field must be a password field of the tab itself (not an embedded document), and the call is judged by the sign-in rule of that site: remembered site or test zone runs, anywhere else a sign-in card asks and offers Always allow. The password is read only after that decision, goes from `op` to the page through the extension, and is redacted from broker output for ten minutes like a sign-in's. Typing literal `text` into a password field stays refused; only the broker's 1Password fill reaches one (content.ts `assertWritable`). Owner direction, 12 Nov 2026: "Gaddi should definitely be able to type passwords."

**EVAL-PASSWORDS.** Evaluation runs on pages with password fields. What their fields hold (in the page, open shadows and readable embedded documents, before and after the evaluation) is replaced by `(hidden)` anywhere in the result, values under four characters excepted. The one denial kept: an expression that reads a password (the word `password` in the extension, the policy's `eval_patterns` in the broker) is refused. Transformed values (encoded, split or reversed) are not recognised. A read-only evaluation cannot send anything anywhere (EVAL-READONLY); a writing script the user approved can.

The agent receives an outcome, site and item title, never a credential field from the sign-in operation. For ten minutes, the broker redacts exact credential matches from text tool output and audit/error records. This does not cover transformed values or screenshot pixels. A visible username or revealed password can still appear in a screenshot. Agents with unrestricted shell access can reach 1Password independently of Gaddi.

### URL credentials

**URL-CREDENTIALS.** Every broker response, error and event redacts credential-bearing URL query and fragment values before delivery, independently of sign-in and policy settings. This includes tab titles/lists, bookmarks, look/frame metadata, eval's automatic page envelope, navigation results and extracted text. Matching includes `code`, `state`, `id_token`, `access_token`, `token`, `sig`, `key`, `password`, `session` and related credential names, with case/encoding variants, repeated parameters and nested redirect URLs. URL userinfo is withheld too. Ordinary query values remain useful. MCP wrappers and CLI output apply the same rule after local formatting.

Redaction is a display/storage boundary, never a navigation rewrite. Chrome, policy checks and signed action hashes still receive the exact original URL; approving one query cannot authorize a different query. Implemented by `shared/url-redaction.ts` and the broker's shared output sink; `tests/redaction/broker.test.sh` tests the real broker/MCP/CLI against synthetic callbacks and falsifies the protection by removing the broker sanitizer in a disposable fixture.

Audit page addresses already omit queries and fragments, but other metadata and legacy restored records can contain URLs. New audit writes and approval-state writes are sanitized. At startup, existing `state.json`, its `.tmp` file and both audit-log generations are scrubbed by private atomic replacement without keeping an unredacted backup. Native-host logs contain fixed lifecycle codes, not URLs; extension storage retains target/window IDs and recovery metadata, not page URLs. Raw URLs needed to act remain in memory. This does not alter Chrome's own history, screenshot pixels, arbitrary secret-bearing page content or previously retained client transcripts. Already exposed credentials and transcript remediation need separate incident handling.

### New accounts and an unreachable password manager

A new account uses `browser_signin` with `create:{title,username,vault}` or `gaddi signin <tab-id> --create '{"title":"Example login","username":"test@example.test","vault":"<vault-id>"}'`. `vault` is the intended vault's ID, not its name. Gaddi shows the vault, title and username on a signed approval, creates a new Login through `op`, then fills the email, an optional confirm-email box (named so, or the second of exactly two email boxes), the password and an optional confirmation. An invisible reCAPTCHA (its badge, notice and `size=invisible` frame) is not a challenge; a visible challenge still is. `op` generates the password internally; no password argument is accepted. It never edits a matching existing item. To retry a previously saved login, select it with `item` and `signup:true` (`--signup` in the CLI).

**NEW-LOGIN.** Creation follows the site's sign-in rule (owner direction, 12 Nov 2026: "be as autonomous as possible when appropriate"): on a site the user chose **Always allow** for, or a test zone, it runs without a card; anywhere else it needs a new signed, single-use approval bound to the origin, tab, title, username and vault, and that card offers Always allow. Refused and protected sites are refused. The privileged fill never presses Enter.

**SIGNUP-SUBMIT.** With `submit:true` (CLI `--submit`) Gaddi presses the form's button after the fill: the form's default submit button, or without a form element the one button (or one sign-up-worded button) near the fields. The press is an ordinary click through every gate, so payment, send, delete and account/security holds still apply; a held press is handed back as `filled` with the approval to use, never retried. `submitted` means the button was pressed, not that the site accepted the account. Without `submit`, complete other fields and submit through ordinary click. Implemented in `daemon/signin.ts`, `daemon/daemon.ts` and `extension/content.ts`; exercised by `tests/signin/helper.test.sh` and `tests/downloads/broker.test.sh`, including changed-vault/username refusal, replay refusal and removal-of-hold falsification.

Each `op` process is bounded to five seconds. An unresponsive or unavailable CLI returns `needs_you` with its OP-DIAGNOSTICS category instead of waiting indefinitely. No phone or Touch ID unlock card is generated by this helper. A create timeout is uncertain: the item may already exist, so inspect 1Password before trying creation again. The browser's 1Password extension and the desktop app are not needed for retrieval or filling; the agents' token file must exist and be readable.

### Page-generated downloads

Use `browser_click` with `download:"/absolute/path/export.zip"`, or `gaddi click <tab-id> <selector> --download /absolute/path/export.zip`. The destination must be a new, non-hidden file under Downloads or the system temporary directory; its parent must already exist. When a capture is held, the signed card names the exact canonical destination. Gaddi writes captured bytes with mode `0600`, never overwrites a file, and returns only the path and byte count. The file's contents remain untrusted.

**DOWNLOAD-CAPTURE.** Capturing a page's own export does not ask by default. Setting `"hold": { "downloads": true }` in the policy file makes every capture ask again; that card binds the origin, tab, target and canonical destination. The click itself is judged as any click: its deny, hold, protected-site, grant and Test-zone rules still apply, so an export button named as a payment, send or delete is held as that click would be (or refused where a deny rule covers it), and a capture never loosens the click's own outcome. The file limits apply with or without a hold: a new, non-hidden file under Downloads or temp, no links or overwrites, re-checked just before writing. Capture is limited to one same-origin `blob:` or `filesystem:` anchor click that reaches the top document, at most 20 MiB, within fifteen seconds. Cross-origin frames, detached anchors, direct navigation and non-anchor JavaScript download methods are unsupported; this is not a general Chrome download manager. Implemented in `daemon/downloads.ts`, `daemon/daemon.ts`, `extension/bg.ts` and `extension/content.ts`; exercised by `tests/downloads/broker.test.sh` for path/overwrite/size guards, no-card default capture, the kept click hold, the opt-in hold with destination-swap refusal, byte readback and a falsification of each, and by `tests/downloads/policy.test.ts` for the policy switch. Production-broker tests use a fake page transport; the disposable-Chrome fixture is a separate acceptance layer.

## Local records

`gaddi audit` records caller labels, action metadata and outcomes. Page addresses omit queries and fragments; credential-bearing URLs in other metadata are redacted too. Typed text and page contents are excluded. Caller labels are supplied by clients, not authenticated operating-system identities. Captures and other state stay in `~/Library/Application Support/Gaddi` by default. Gaddi forwards page content to the connected agent, whose model provider and data policy you choose separately.
